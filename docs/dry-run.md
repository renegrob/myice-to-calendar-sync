# Dry run

`./run-local.sh` is a **dry run by default**. It computes the real sync plan — the same `plan_sync()` a live sync uses, built from the actual myice feed and the actual state of your Google Calendars — and writes it to a report file. It never calls `events().import_()` or `events().delete()`; nothing on your calendars changes.

## It still needs the service-account key

A dry run **does read your calendars** (`events().list()`) in order to compute a real create/update/delete/unchanged diff, rather than a guess based on the feed alone. That means it needs the same Google service-account key a live `--apply` does — set `GOOGLE_SERVICE_ACCOUNT_FILE`, or place `.google-service-account.json` in the project root (see `run-local.sh`'s own `--help`).

This is a deliberate trade-off against this project's ancestor's old `--preview` mode, which needed no key at all because it only looked at the feed and never consulted the calendar. The upside of the current dry run is that its report is trustworthy — "2 created, 1 updated" really means what a live run would do, not just "2 records look new to the feed." The cost is that a dry run is no longer something you can run with zero Google access configured.

## Flags

From `run_local.py` / `run-local.sh --help`:

| Flag | Effect |
|---|---|
| *(none)* | Dry run (default): plan only, write a report. |
| `--apply` | Live sync: same code path as the deployed Lambda. Creates/updates/deletes real events. |
| `--games-only` | Only plan/sync entries with `myice_event_type == "g"`. |
| `--trainings-only` | Only plan/sync entries with `myice_event_type == "p"`. |
| `--out PATH` | Dry-run report file path. Defaults to `dry-run-<UTC timestamp>.txt` in the project root. |
| `--since YYYY-MM-DD` | Dry-run only. Overrides the configured `myice_min_date` and allows the plan to include past events. |
| `-h` / `--help` | Show usage (via `run-local.sh`). |

`--games-only` and `--trainings-only` are mutually exclusive, as are `--dry-run`/`--apply` (though `--dry-run` is also just the default with no flags).

## `--since` cannot be combined with `--apply`

```
--since is dry-run only; a live sync never touches the past.
```

`run_local.py` enforces this with `parser.error(...)` before anything runs. The reason is the **past-event guard**: `plan_sync()` in `calendar_sync.py` takes an `allow_past` flag that is `False` for every live sync (deployed Lambda or local `--apply`) and can only be set `True` by a dry run via `--since`. With the guard on, an event whose end time has already passed is never created, updated, deleted, or tombstoned — it's left exactly as it is, treated as settled history. `--since` exists specifically so you can temporarily lift that guard *in a dry run* to inspect what a past date range would have produced, without any risk of it mutating real history.

This is a deliberate change from this project's ancestor, where an event whose UID simply left the feed was deleted regardless of how long ago it had already happened. Here, once an event is in the past, nothing — not a status change, not it disappearing from myice entirely — touches it anymore.

## Report format

The report is plain text, one section per configured club entry, generated by `dry_run.render_report()`. Example (club IDs/calendar redacted to generic placeholders, otherwise unedited output):

```
myice-to-calendar-sync DRY RUN
generated 2026-10-01T18:56:46+00:00
nothing was created, updated or deleted

========================================================================
[0] club 42 (games) -> family@gmail.com  prefix myice-a-game-
========================================================================
  CREATE    2026-10-05 19:30  U13 vs Lions
  CREATE    2026-10-05 18:30  Warm-up: U13 vs Lions [prep]
  UPDATE    2026-10-12 19:30  ❓ U13 vs Tigers
      summary: 'U13 vs Tigers' -> '❓ U13 vs Tigers'
  DELETE    myice-a-game-duty-998-ab12cd34 [duty]
  1 unchanged

  2 created, 1 updated, 1 deleted, 1 unchanged, 0 tombstoned
```

Notes on reading it:
- `[prep]` and `[duty]` tags mark preparation and duty entries, respectively (plain events have no tag).
- Every `UPDATE` line is followed by an indented field-level diff — one line per changed field, old value then new — so you can see exactly what would change before anything is written. It compares the same fields (`calendar_sync._COMPARE_FIELDS`) that decide whether an event counts as "unchanged" at all, and that `execute_plan()`'s own `UPDATE DIFF` log line uses in apply mode, so the dry run and a live run always agree about what counts as a change.
- `DELETE` lines show the UID rather than a title, since the body being deleted isn't necessarily still available to describe.
- A `❓` prefix on a title (from `request_summary_format`) means that record's status is "Temporär" — see `docs/statuses.md`.
- The report is printed to stdout **and** written to the report file — if the file write fails (e.g. a bad `--out` path), the report is not lost; it was already on stdout, and `run_local.py` exits non-zero to flag the write failure.
